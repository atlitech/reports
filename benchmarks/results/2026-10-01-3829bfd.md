> Engine 3829bfd (long-lived browser, chrome-headless-shell image) vs Gotenberg 8.37.0. Run after all agent work finished; other unrelated containers (dapr, a minecraft e2e bridge) were running on the Docker VM, so the host was not fully idle.

- **Mode:** full · **targets:** atli, gotenberg · **engine commit:** `3829bfd feat(engine): long-lived isolated browser, bounded queue, streaming, and a hardened server (#126)` (HEAD `3829bfd` on `docs/benchmark-results`)
- **Per target container:** 2 CPUs, 2g memory (swap off), started fresh for every cell; one container at a time
- **Each cell:** fresh container → 5 s warm-up (at most 4 workers, drained) → measured phase: N closed-loop workers start requests for 30 s, then in-flight requests finish; client timeout 30 s
- **Host:** Apple M1 Max, 10 logical cores, 64 GiB RAM, macOS 26.6.2 (Arm64); load average 5.08 7.62 8.75 at start, 5.40 5.74 6.48 at end

How to read this: `docs/s` is the number of valid PDFs the measured phase produced divided by its wall time (drain included). Latency percentiles cover the successful requests; failed requests are counted under *errors*, by class (`http_<status>`, `client_timeout`, `transport_*`, `invalid_pdf`). *CPU s/doc* is the container's CPU time per valid PDF — the cost of a document, and the number least distorted by other load on the machine. *Peak mem* is the highest `docker stats` reading (usage minus page cache, ~1 s sampling). See `benchmarks/README.md` for the full methodology.
