# Load benchmark: Atli.Reports vs Gotenberg — 2026-10-01 (287f9bc)

> PROVISIONAL baseline of today's engine (engine commit 14c01a7: a browser is launched for every conversion). Recorded on a shared Apple-silicon Mac while two other agents were building and running Chrome-heavy test suites, so the host was under concurrent load (load averages below and per cell); absolute numbers are noisy, CPU s/doc is the most robust column. Rerun on a quiet machine before publishing a comparison.

- **Mode:** quick · **targets:** atli, gotenberg · **engine commit:** `14c01a7 feat(engine): import the HTML-to-PDF engine as Atli.Reports.Engine and Atli.Reports.Server (#123)` (HEAD `287f9bc` on `feat/benchmarks`)
- **Per target container:** 2 CPUs, 2g memory (swap off), started fresh for every cell; one container at a time
- **Each cell:** fresh container → 3 s warm-up (at most 4 workers, drained) → measured phase: N closed-loop workers start requests for 10 s, then in-flight requests finish; client timeout 30 s
- **Host:** Apple M1 Max, 10 logical cores, 64 GiB RAM, macOS 26.6.2 (Arm64); load average 4.84 7.33 12.57 at start, 7.38 6.98 10.74 at end

How to read this: `docs/s` is the number of valid PDFs the measured phase produced divided by its wall time (drain included). Latency percentiles cover the successful requests; failed requests are counted under *errors*, by class (`http_<status>`, `client_timeout`, `transport_*`, `invalid_pdf`). *CPU s/doc* is the container's CPU time per valid PDF — the cost of a document, and the number least distorted by other load on the machine. *Peak mem* is the highest `docker stats` reading (usage minus page cache, ~1 s sampling). See `benchmarks/README.md` for the full methodology.
